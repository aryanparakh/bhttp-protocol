## 3. Deep-Dive Audit of Critical Protocol Vectors

### Vector 1: 12-Byte Fixed Header Layout & Endianness
- **Specification (`SPEC.md §5`)**:
  - `0x0000 - 0x0001`: Magic (`0xB748`) [2 octets]
  - `0x0002`: Version (`0x01`) [uint8]
  - `0x0003`: Frame Type (`0x01` - `0x03`) [uint8]
  - `0x0004`: Flags (bit 0 `CONN_CLOSE`) [uint8]
  - `0x0005`: Reserved (`0x00` transmitted) [uint8]
  - `0x0006 - 0x0007`: Status Code [uint16 BE]
  - `0x0008 - 0x000B`: Payload Length [uint32 BE]
- **Implementation Check**:
  - `src/protocol/constants.py`: `FRAME_HEADER_FMT = '>2sBBBBHI'`, size verified by `struct.calcsize(FRAME_HEADER_FMT) == 12`.
  - Byte order prefix `>` explicitly enforces big-endian network byte order.
- **Wire Capture Verification**:
  - `examples/request.hex`: `B7 48 01 01 01 00 00 00 00 00 00 2F`
    - Magic: `B7 48`
    - Version: `01`
    - Type: `01` (REQUEST)
    - Flags: `01` (CONN_CLOSE)
    - Reserved: `00`
    - Status: `00 00` (zero)
    - Payload Length: `00 00 00 2F` (47 bytes big-endian)
- **Verdict**: Exact byte-level conformance.

### Vector 2: Unknown Frame Skipping (Forward Compatibility)
- **Specification (`SPEC.md §10`)**: Receivers encountering unknown frame types must read the 12-byte header, validate magic, version, and payload length <= `MAX_PAYLOAD_SIZE`, discard `payload_length` bytes, and continue reading the next frame on the same TCP connection.
- **Implementation Check**:
  - Server (`src/server/connection.py` lines 62–71):
    ```python
    if header.frame_type not in (FRAME_REQUEST, FRAME_RESPONSE, FRAME_ERROR):
        discard_bytes(conn, header.payload_length)
        continue
    ```
  - Client (`src/client/main.py` lines 137–146):
    ```python
    if header.frame_type not in (FRAME_RESPONSE, FRAME_ERROR):
        continue
    ```
- **Test Evidence**:
  - `test_unknown_frame_type_skipped_cleanly`: Sent unknown frame opcode `0x77` with 16 bytes of payload over an open TCP socket, immediately followed by `GET /test.txt`. The server cleanly discarded the 16 bytes and returned `200 OK` with the exact body for `/test.txt`.
- **Verdict**: Fully compliant.

### Vector 3: Path Traversal & Security Sandbox
- **Specification (`SPEC.md §12`)**: Paths must start with `/`, must not contain `..` path components, must not contain Windows drive letters, and resolved targets must be verified descendants of document root.
- **Implementation Check**:
  - `src/server/filesystem.py` (`resolve_path`):
    - Normalizes `\` to `/`.
    - Splitting path parts explicitly rejects `..`.
    - Strips leading `/` and tests for drive pattern `[a-zA-Z]:`.
    - Canonicalizes root and target via `os.path.realpath` and enforces substring prefix match: `candidate_real.startswith(doc_root_real + os.sep)`.
- **Test Evidence**:
  - `test_path_traversal_returns_400`: `GET /../../etc/passwd` returns status `0x0190` (400 Bad Request).
  - `test_windows_drive_letter_returns_400`: `GET /C:/Windows/System32/cmd.exe` returns status `0x0190` (400 Bad Request).
- **Verdict**: Fully compliant.

### Vector 4: Real Wire Hex Dump Artifacts
- **Audit Question**: Were `examples/request.hex` and `examples/response.hex` manually typed or actually captured from the socket?
- **Verification**:
  - Executed generator script that bound an active socket, spawned the server, dispatched a real client frame, captured the raw octets off the socket buffer, wrote `request.bin` and `response.bin`, and rendered `request.hex` and `response.hex`.
  - The hex files match the exact binary files byte-for-byte.
  - `examples/annotated-hexdump.md` was compared against `request.hex` and `response.hex`. All offsets (e.g. `0x0000` to `0x003A` for request, `0x0000` to `0x02EF` for response) align to the exact byte values.
- **Verdict**: Genuine captured wire traces, perfectly documented.
